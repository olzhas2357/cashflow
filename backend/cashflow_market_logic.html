Two market modes
Auction mode
Triggered when a player draws a Deal card (small or big). The card is shown to all players. All players can bid. Highest bidder wins. Card holder can also accept original card price (no auction needed).
Card-triggered
Direct trade
Card holder passes on a deal but offers it to one specific other player at a negotiated price. Bilateral agreement — both must confirm. Auditor then approves.
Player-to-player
Who can initiate a market event
Only the player who drew the deal card can start a market event — either by opening an auction OR by offering the deal directly to another player. Other players cannot list or sell assets they already own. The market is purely deal-card driven.
Card holder only
Auditor's role in all transactions
What auditor controls
Approves or rejects every completed deal (auction win or direct trade confirmation). Verifies buyer has enough cash. Applies financial changes to both players' sheets.
Final authority
What auditor does NOT control
Setting bid amounts, opening prices, or negotiated prices — that's between players. The auditor only validates the final agreed transaction.
Not a price setter
Key constraint
buyer.cash >= deal.down_payment → transaction allowed buyer.cash < deal.down_payment → auditor must REJECT

Auction rules
1
Opening price = card's listed price
The deal card has a printed cost and down_payment. The auction opening bid starts at down_payment (what buyer actually pays in cash). Card holder can also just accept the printed price themselves — no auction needed.
2
Card holder cannot bid in their own auction
They already had first right to take the deal. If they open auction, they pass — only other players can bid.
3
Each bid must exceed the previous bid
Min increment can be set by auditor (e.g. $500 or $1,000). Bids are visible to all players in real time via WebSocket.
4
Auction timer or auditor closes it
Either a countdown timer (e.g. 60 seconds of inactivity) or the auditor manually closes bidding. When closed: highest bidder wins.
5
Card holder gets cash from winning bid
The card holder receives the winning bid amount as cash. This simulates "flipping" a deal. The card asset transfers to the winning bidder at the bid price (their down_payment = bid amount).
6
No bids = auditor cancels or card holder keeps it
If no one bids, the deal is cancelled or card holder can choose to take it themselves.
Financial effect (auction win)
Card holder: cash += winning_bid_amount Winning bidder: cash -= winning_bid_amount assets += deal (with cashflow, liability if any) if deal has mortgage: liabilities += mortgage_amount expenses += monthly_payment
Direct trade flow
Card holder passes on deal
→
Selects a specific player to offer to
→
Sets offer price (can be any amount)
→
Target player: Accept / Reject
→
Both confirmed → auditor approves
Rules for direct trade
1
Card holder sets the price freely
No minimum. Card holder can offer the deal below, at, or above the printed card price. This simulates negotiation and charity deals between friends.
2
Only one offer at a time
Card holder can only offer to one player at a time. If rejected, they can then offer to someone else OR open an auction OR take the deal themselves.
3
Offer expires after a time limit or rejection
Target player must respond within e.g. 2 minutes or the offer auto-expires and returns to card holder.
4
Card holder receives negotiated price
Same as auction — card holder gets cash equal to the agreed price. The deal asset transfers to the buyer.
Financial effect (direct trade)
Card holder: cash += agreed_price Buyer: cash -= agreed_price assets += deal if deal has mortgage: liabilities += mortgage_amount expenses += monthly_payment
Edge case: card holder keeps the deal
At any point the card holder can say "I'll take it myself" — they pay the printed down_payment, get the asset, and no market event happens. This is the default behavior from the original game. Market events are optional on top.
Always available as fallback
Market deal lifecycle
open
Card drawn, card holder deciding: keep / auction / offer
→
bidding
Auction active, players placing bids, timer running
→
pending
Winner/buyer chosen, waiting for auditor approval
completed
Auditor approved, financials applied to both players
rejected / expired
Auditor rejected, no bids, or offer timed out
State transitions
  • open → bidding — auditor clicks "Open auction" on the active deal card
  • open → pending — card holder makes direct offer AND target player accepts
  • open → completed — card holder takes deal themselves (no market event needed)
  • bidding → pending — auditor closes auction, highest bidder identified
  • bidding → expired — no bids placed, auditor closes with no winner
  • pending → completed — auditor approves: cash/assets updated for both players
  • pending → rejected — auditor rejects: buyer didn't have cash, or auditor cancels
  • rejected → open — card holder can retry: new auction or different offer
Who can trigger each transition
Card holder actions
Open auction · Make direct offer · Take deal themselves · Cancel their own offer (before acceptance)
Target player actions
Accept direct offer · Reject direct offer · Place bid (auction only)
Auditor actions
Open auction · Close auction · Approve pending deal · Reject pending deal · Force cancel any deal
System (auto)
Expire offer after timeout · Auto-close auction after inactivity timer · Validate cash on every bid

Auditor approval checklist (before clicking Approve)
1
Buyer has enough cash
buyer.cash >= deal.down_payment. If auction, down_payment = winning_bid. If direct trade, down_payment = agreed_price.
2
Card holder is still in the game
Edge case: if card holder went bankrupt between deal open and approval, auditor cancels.
3
Deal card is still "open" (not already taken)
Prevents double-approval race condition.
4
Check passive income after approval
After applying changes, system checks if buyer's passive_income >= total_expenses → escape rat race trigger.
New DB table: market_deals
CREATE TABLE market_deals (
  id            UUID PRIMARY KEY,
  game_id       UUID REFERENCES games(id),
  card_holder_id UUID REFERENCES players(id),
  card_id       UUID REFERENCES deal_cards(id),
  mode          TEXT, -- 'auction' | 'direct'
  status        TEXT, -- 'open'|'bidding'|'pending'|'completed'|'rejected'|'expired'
  target_player_id UUID REFERENCES players(id), -- direct trade only
  offered_price INTEGER,             -- direct trade price
  winning_bid   INTEGER,             -- auction winner amount
  winner_id     UUID REFERENCES players(id),
  auditor_note  TEXT,
  expires_at    TIMESTAMPTZ,
  created_at    TIMESTAMPTZ DEFAULT now(),
  resolved_at   TIMESTAMPTZ
);
New DB table: auction_bids
CREATE TABLE auction_bids (
  id           UUID PRIMARY KEY,
  market_deal_id UUID REFERENCES market_deals(id),
  player_id    UUID REFERENCES players(id),
  amount       INTEGER NOT NULL,
  created_at   TIMESTAMPTZ DEFAULT now()
);
Go API endpoints (add to your handlers)
// Card holder opens market event
POST /games/:id/market/open
  body: { card_id, mode: "auction"|"direct", target_player_id?, offered_price? }

// Auditor opens bidding (auction only)
POST /games/:id/market/:deal_id/start-auction

// Player places bid
POST /games/:id/market/:deal_id/bid
  body: { player_id, amount }
  validate: amount > current_highest_bid && player != card_holder

// Target player responds to direct offer
POST /games/:id/market/:deal_id/respond
  body: { player_id, action: "accept"|"reject" }

// Auditor closes auction → sets winner
POST /games/:id/market/:deal_id/close-auction

// Auditor approves → applies financials
POST /games/:id/market/:deal_id/approve
  validates: buyer.cash >= final_price
  applies: cash delta both players, asset to buyer, check escape condition

// Auditor rejects
POST /games/:id/market/:deal_id/reject
  body: { note? }
